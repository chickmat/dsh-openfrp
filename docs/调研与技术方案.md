## 0. 结论速览（先看这段）

| 问题 | 结论 | 依据 |
|---|---|---|
| **有没有人已经做过？** | **没有 OpenFrp 方向的。** 但生态里已有 **60+ 个"暴露本地服务"的隧道插件**（cloudflared/Tailscale/ngrok/cpolar），frp 家族有 3 个"自备 frps"的 | §2.1 / §12 |
| **这件事有没有必要做？** | **有**——但要按 v2 的定位：不是"第 61 个隧道插件"，而是**全流程开服助手 / 通用"服务↔隧道"协调器** | §12 / §14 |
| **真正的痛点是什么** | **不是做不到，而是 DSH 没有眼睛**：设置他看不见、日志他读不到、报错他没有证据 → 只能指挥用户、再听用户复述，几小时就这么烧掉 | §12.1 |
| **技术上能不能做？** | **能，且关键环节已实测**：MC 实时日志 ✅、运行中发命令 ✅、OpenFrp API ✅、frpc CLI ✅ | §13 |
| **最大的技术难点** | 官方"远程安全登录"用 **XSalsa20-Poly1305**，**Node 内置 crypto 不支持**，需引 `tweetnacl`（已定：走这条路） | §6.2 / §14.2 |
| **与官方启动器的关系** | **可以共存**。冲突是**按隧道**计的，不是按进程/账号计的 → 插件**只拥有自己创建的隧道** | §12.2 / §14.3 |
| **最大的人为风险** | OpenFrp 服务条款（必须带 UA、必须明显位置声明、**禁止自动签到**） | §17 |
| **工作量估计** | 核心闭环（登录+隧道+挂靠+日志+命令+暴露）约 **3～5 天**；加 GUI 面板 **5～8 天** | §16 |
| **建议** | 按 §16 的 P0～P7 推进，每个阶段都有可实测的验收点 | §16 |

**一句话**：这个插件的价值不在"能开服"，也不在"能穿透"——而在**让 DSH 在这条链路上有自己的眼睛和手，人类不再充当数据中转站**（§12.1）。你给的 4 个链接里，**真正必需的是 `OPENFRP-APIDOC` 和 `OpenFrp-Docs`**；两个启动器仓库的价值是"照抄实现逻辑"而非"当依赖"；你**漏掉了 4 个更该看的仓库**（§3.3），而且你本机装的官方启动器**并不是**你给的那个 WinUI 仓库（§3.2）。

### 1.3 实测踩到的两个坑（写方案时必须绕开）

1. **`Invoke-WebRequest` / `Invoke-RestMethod` 在本机沙箱内必然失败**（`基础连接已经关闭`）。
   这是沙箱受限令牌拿不到 Windows 密钥库导致的 **schannel** 问题，**不是网络问题**。
   → 结论：插件里所有 HTTP 请求走 **Node 内置 `fetch`（OpenSSL）**，不要用 .NET 客户端。（已实测 `fetch` 完全正常，见 §6.1）
2. **`dsh plugin` 命令在 DSH 沙箱内跑会 EPERM**：
   ```
   Error: EPERM: operation not permitted, open
   'C:\Users\Admin\.dsh\profiles\web\package.json.lock'
   ```
   因为 `~/.dsh/profiles` 在会话工作区（`C:\DSH`）之外，`workspace-write` 沙箱不允许写。
   → 结论：**插件的安装/注册动作必须由你在 DSH 之外的普通终端里执行**（或者临时放开为 `danger-full-access`）。这条会写进 §8 的步骤里。

## 2. 必要性论证：有没有人做过？值不值得做？

### 2.1 排查结果：**没有同类 DSH 插件**

搜索范围与结果：

| 搜索方式 | 结果 |
|---|---|
| GitHub 仓库搜索 `openfrp dsh` / `frp dsh plugin` | **0 条** |
| `gh search repos --topic dsh-plugin openfrp` | 无关结果（GitHub 的 topic+关键词组合未生效，返回的是通用热门仓库） |
| npm registry 搜 `dsh-plugin openfrp` / `dsh-openfrp` | **没有任何 OpenFrp 插件** |
| 遍历 DSH 插件聚合目录（awesome-dsh-plugin 等 12 个仓库） | 未发现 OpenFrp / frp 条目 |

**注意一个搜索陷阱**：`gh search repos --topic dsh-plugin tunnel` 返回了 `fatedier/frp`（10.9 万星）和 `deepseek-ai/deepseek-harness`，这是 GitHub 把关键词和 topic 混在一起做全文检索的结果，**不代表有该插件**。真正可靠的证据来自 **npm registry**，那里查 `dsh-plugin openfrp` 是干净的 0 结果。

### 2.2 但是：生态里已经有人证明了"这个需求成立"

搜索时挖到两个**很有说服力**的旁证：

**① `dsh-plugin-tunnel@0.1.1`（MIT，2026-09，[loadchange/tunnel-dsh-plugin](https://github.com/loadchange/tunnel-dsh-plugin)）**

> "把任意 dsh 插件的 **loopback 看板**，按需、限时、可撤销地暴露到公网——并且只做这一件事。"

- 它做的是 **Cloudflare Named Tunnel**，不是 OpenFrp；
- 给模型的是一个 `tunnel_control` 工具（`list` / `status` / `open` / `close` / `close-all`）；
- 架构上高度"运维向"：依赖 **Linux + root + systemd**（`/etc/dsh-tunnel/targets/*.conf`、`RuntimeMaxSec` drop-in、每 10 秒看门狗）。

→ **含义**：①"AI 自己开隧道"这个需求已经被验证过了，不是我们的臆想；②但那个实现**在 Windows 上根本跑不起来**，而你是 Windows。

**② `dsh-remote-cpolar@1.3.0` 和 `dsh-mobile@0.5.5`**

这两个是"手机远程使用 DSH"的插件。它们的 README 明确写着：

> v1.3.0 起**不再依赖 cpolar**：任意内网穿透工具（cpolar / **frp** / ngrok / natapp 等）把公网 URL 转发到本机 `127.0.0.1:8090` 即可使用。
> 穿透工具负责"公网可达"，插件负责"让 dsh 把远程请求当本机请求"。**插件与穿透工具解耦**。

→ **含义**：远程访问类插件**故意把隧道这一层留空了**，让用户自己找工具。**这个空位就是我们要填的位置**——而这些插件正好是天然的"下游消费者"（§7.4）。

### 2.3 必要性评分

> ⚠️ **本节已被 v2 更正**：下面"生态空白"的说法**过于乐观**。后续的生态盘点查明 DSH 里已有 **60+ 个"暴露本地服务"的隧道插件**。准确的表述是：**OpenFrp 这个后端是空白，但"暴露本地服务"这个需求是红海**。完整更正见 **§12**。

**支持做的理由（正面）**

1. **后端真空**：`openfrp` 在 4415 条插件目录 + npm 全量里 **0 命中**；frp 家族只有 3 个"自备 frps"的（star ≤5）；
2. **你本人就是目标用户**：本机装了官方启动器 5.8.93、有 frpc、有隧道 33316、有 frpc 工作目录；
3. **对国内环境比 Cloudflare 更实用**：OpenFrp 免费、有 20+ 国内/港澳台/海外节点，延迟远低于 Cloudflare 回源；你本来就在用；
4. **有 cloudflared 给不了的差异化**：**TCP/UDP + 固定远程端口**（Minecraft 联机、SSH、数据库），quick tunnel 只能给随机域名 HTTP；
5. **AI 加持下有真正的增量**：手动开隧道是"点面板 → 选隧道 → 启动"；插件能做到"**我把本地 8000 端口暴露出去，给我地址**"一句话完成，并且**新建隧道**（官方面板要填 13 个字段）可以由 AI 按语义自动填；
6. **实现成本低**：frpc 是单文件 exe + 简单 CLI，API 有完整文档，不用逆向。

**反对做的理由（反面，必须诚实列出）**

1. **"暴露本地服务"是红海**：DSH 里同类插件 60+，头部 `dsh-pocket` 1514★、`dsh-mobile` 369★、`dsh-bridge` 183★；**如果目标只是"随手开个隧道给个网址"，用 cloudflared 更省事，OpenFrp 是净增摩擦**；
2. **定位重叠**：`dsh-plugin-tunnel`（Cloudflare Named Tunnel 生命周期，npm）与"隧道 CRUD + 生命周期"几乎同构；
3. **进程管理有冲突风险**：同一条隧道被重复开启会撞 `proxy conflict` / `multi-instance racing`（官方排错文档明确列了）；
4. **要承担服务条款责任**：必须带 UA、必须在明显位置声明使用 OpenFrp OPENAPI、**绝对不能做自动签到**；
5. **API 文档自己声明"某些地方可能过时或有误"**，且官方写明"没有义务为您解决开发中遇到的问题"——无 SLA、无稳定契约；
6. **维护成本**：非官方 OpenFrp 库全部 0–2★ 且停在 2023–2025，**只能抄逻辑不能依赖**；frpc 版本迭代快（本机 0.67.0，最新 0.68.0）。

**结论（v2 更正后）**：**值得做，但不是作为"又一个隧道插件"**。
判据是插件**解决的是不是 DSH 的"瞎"**——如果它的价值只是"省掉点面板的几步"，那不值得；
如果它的价值是**让 DSH 能自己看见日志、自己发命令、自己拿到公网地址、自己定位故障**，那就值得。
v2 的定位见 **§14**，实施计划见 **§16**。

### 3.2 一个重要的澄清：你本机装的不是这个仓库

你本机装的是 **`OpenFrp Launcher 5.8.93`**，目录里是 `iNKORE.UI.WPF.Modern.dll` → 这是 **WPF** 版；而 `OpenFrp.Launcher.WinUI` 是 **WinUI 3** 版。**两者是不同产品线**。

这带来两个实际后果：

1. 拿 `OpenFrp.Launcher.WinUI` 的源码去对照本机文件路径、配置格式，会**对不上**；
2. 但它也不是完全没用——它揭示了官方架构里有 **`OpenFrp.Service.exe` 辅助进程**（本机同样存在），通过 **gRPC over Named Pipe**（`GrpcDotNetNamedPipes.dll`、`Grpc.Core.dll`）通信，并且用了 **`Tomlyn.dll`（TOML 解析，对应 frpc.toml）**、**`NaCl.dll`（curve25519，对应 argo 登录）**。

→ **对本插件最有价值的一条**：官方是"**GUI 进程 + 后台 Service**"分层，隧道跑在 Service 里，所以关掉窗口隧道不断。
我们的插件是**另一种分层**：**DSH 宿主进程 + frpc 子进程**。理解了官方为什么这么分，就理解了插件为什么必须自己管进程生命周期（§7.3）。

## 4. 从链接里提炼的核心情报

### 4.1 API 总表（已交叉验证：官方文档 + CrossPlatformLauncher 源码）

- **主地址**：`https://api.openfrp.net`
- **备用地址**：`https://of-dev-api.bfsea.com`（CPL 源码里用的是这个）
- **登录服务**：`https://access.openfrp.net`（argoAccess）
- **响应格式**：所有接口都返回 `{ flag: boolean, msg: string, data: any }`，`flag=false` 即失败，`msg` 是给人看的错误原因
- **Content-Type**：`application/json`

| # | 接口 | 方法 | 路径 | 作用 |
|---|---|---|---|---|
| 1 | 获取用户信息 | POST | `/frp/api/getUserInfo` | 用户名/邮箱/用户组/带宽/剩余流量/**token** |
| 2 | 获取隧道列表 | POST | `/frp/api/getUserProxies` | 全部隧道 + 在线状态 |
| 3 | 获取节点列表 | POST | `/frp/api/getNodeList` | 全部节点（含是否支持 tcp/udp/http/https/stcp/xtcp） |
| 4 | 新建隧道 | POST | `/frp/api/newProxy` | 13 个字段 |
| 5 | 编辑隧道 | POST | `/frp/api/editProxy` | 同上 + `proxy_id` |
| 6 | 删除隧道 | POST | `/frp/api/removeProxy` | `{proxy_id}` |
| 7 | 刷新隧道状态 | POST | `/frp/api/refreshProxyStatus` | `{proxy_id}`，强制服务端刷新在线状态 |
| 8 | 可用节点 | GET | `getAvailableNode` | CPL 用（文档未列） |
| 9 | 节点配置 | POST | `getNodeConf` | `{node_id}`，CPL 用（文档未列） |
| 10 | 节点状态 | GET | `getNodeStatus` | CPL 用（文档未列） |
| 11 | 签到信息 | POST | `getSignInfo` | ⚠️ **只读展示，不自动签** |
| 12 | 重置令牌 | POST | `resetToken` | 危险操作 |
| 13 | 登出 | POST | `logout` / `logoutAll` | — |
| 14 | **纯 token 拿隧道列表** | GET | `/api?action=getallproxies&user=<token>` | **只需 token，无需登录**；返回按节点分组的精简列表（含**公网地址** `remote`） |
| 15 | **软件/版本信息** | GET | `/commonQuery/get?key=software` | frpc 最新版本 + 下载源（用来下载/更新 frpc） |

**第 14 条特别重要**：它**只需要 32 位用户 token**（不是 Authorization），就能拿到"节点 → 隧道 → `remote` 公网地址"的完整映射。这意味着——

> **即使完全不做登录流程，插件也能实现"列出我的隧道并告诉我每条的公网地址"这个最核心的价值。**

这是一个非常重要的"低成本切入点"（§7.2 的 v1 就靠它）。

### 4.2 鉴权：三种方案，各有取舍（**需要你选，见 §10 问题 5**）

| 方案 | 怎么做 | 有效期 | Node 实现难度 | 评价 |
|---|---|---|---|---|
| **A. 复用官方启动器的凭据** | 读 `%LOCALAPPDATA%\OpenFrp.Launcher\...\user.config`，里面有现成的 Authorization | 跟随官方客户端 | ⭐ 极简（读一个 XML） | **最省事**，但依赖官方启动器已登录；属于"读别人的文件"，要征得你同意 |
| **B. 用户手动粘贴 Authorization** | 在 OpenFrp 面板 →「个人中心 → 第三方客户端安全登录」复制，粘到 DSH 插件设置里 | **最长 30 天** | ⭐ 简单（HTTP Header） | **官方明确推荐的第三方接入方式**，最稳 |
| **C. 完整实现远程安全登录（argoAccess）** | X25519 密钥对 → `requestLogin` → 拉起浏览器 → 每 5 秒轮询 `pollLogin` → 解密拿 Authorization | 会话式 | ⭐⭐⭐⭐ 复杂 | 体验最好（不用手动复制），但**需要额外 npm 包**（§6.2） |
| D. OAuth2（Natayark ID） | `account.naids.com` 走 OAuth 拿 code → 换会话 | 8 小时 | ⭐⭐⭐⭐ 复杂 | 文档标注"优先推荐 Remote Login"，且要处理 Cookie，**不建议 v1 做** |

补充事实：
- 隧道**在线状态**和**节点列表**：`getNodeList` 不带 Authorization 会返回 `{"flag":false,"msg":"登入凭证无效，请先登入"}`（**已实测**），所以必须鉴权；
- **每次请求的响应头有概率返回新的 Authorization**，需要自动更新（CPL 就是这么做的：响应头里的 `authorization` 与本地不一致就覆盖）；
- **429 限流**：官方反复强调"务必定义退出逻辑"，轮询建议 1 次 / 5 秒、最长 5 分钟。

## 5. 从 CrossPlatformLauncher 源码提炼的参考实现（可直接翻译成 JS）

我把关键 Rust 源码抓到了 `C:\DSH\_openfrp-research\cpl-*.rs`，以下是可复用的部分。

### 5.1 API 调用 + Authorization 自动刷新（`src/utils/apiClient.ts`）

- 所有请求过一层 `callApi(endpoint, {method, headers, body})`，自动带上 `Authorization`；
- **响应头里的 `authorization` 与本地不一致就更新**（官方要求的自动更新机制）；
- 统一检测 `flag === false` 且 `msg` 匹配 `/未登录|登录失效|token 失效|凭证失效|unauthorized/` → 清理本地登录态并通知 UI。

→ **插件应当照抄这套"鉴权失效即重登"的状态机**，否则用户会遇到"莫名其妙所有操作都失败"。

### 5.2 frpc 进程管理（`src-tauri/src/main.rs` 的 `start_frpc_instance`）

核心逻辑（约 100 行 Rust，翻译成 JS 大概 60 行）：

```
1. 查进程表，同一隧道已在跑 → 报错"该隧道已经在运行中"
2. 组装命令：  frpc -u <token> -p <tunnelId>
             + 可选 --use-doh / --debug / --force-tls / --doh-addr
             + Windows 下 CREATE_NO_WINDOW（不弹黑窗）
             + 可选清空 HTTP_PROXY/HTTPS_PROXY 等环境变量（绕过代理）
3. spawn，stdout 和 stderr 各起一个线程按行读
4. 每行日志 emit 成事件 `frpc-log-<隧道ID>` → 推给前端
5. 把 child 存进 HashMap<隧道ID, ProcessInfo{child, name, remote, pid}>
6. 停止：Windows 用 taskkill /PID <pid> /T
```

**对我们最有价值的三个细节**：

- **必须 `CREATE_NO_WINDOW`**，否则每开一条隧道弹一个黑框（Node 里对应 `windowsHide: true`）；
- **stdout 和 stderr 分开读**（frpc 的日志等级输出到不同流）；
- **进程表以隧道 ID 为键**，天然解决"同一隧道不能开两次"的问题。

### 5.3 argo 远程登录的完整实现（`src-tauri/src/argo_access.rs`）

这是**全流程最精确的参考**，逐步骤还原如下：

```
1. 生成 X25519 密钥对 (sk, pk)，pk 做 base64url(padded) → public_key_b64
   并把这个 (sk, pk) 按 request_uuid 存起来（一次性，不复用）

2. POST https://access.openfrp.net/argoAccess/requestLogin
   body: {"public_key": public_key_b64}
   → 返回 {code:200, data:{authorization_url, request_uuid}}
   → 把 authorization_url 用系统浏览器打开，让用户点"同意"
   → 429 视为限流

3. 轮询 GET https://access.openfrp.net/argoAccess/pollLogin?request_uuid=<uuid>
   每 5 秒一次，最多 60 次（= 5 分钟）
   - HTTP 204 → 授权还没完成，继续等
   - HTTP 429 → 限流，继续等
   - HTTP 200 + code:200 → 进入解密

4. 解密：
   - 从【响应头】 x-request-public-key 取服务端公钥（base64，可能要补 padding）
   - data.authorization_data 做 base64 解码 → 前 24 字节是 nonce，其余是密文
   - 用 NaCl box（X25519 + XSalsa20-Poly1305）解密 → 明文就是 Authorization
   - 解完立刻销毁本次密钥对
```

源码里还贴心处理了 base64 的四种变体（URL_SAFE / STANDARD × 带/不带 padding），**说明服务端返回的 base64 格式不稳定，实现时要做兼容**。

### 5.4 frpc 下载与更新（`download_frpc`）

### 5.5 frpc 日志语义表（**做日志解析必读**，来自官方排错文档）

| frpc 日志原文 | 含义 | 插件该怎么处理 |
|---|---|---|
| ``Your `XXX` proxy is available now. Use [`YYY`] to connect.`` | ✅ **隧道启动成功** | **正则捕获 `YYY` 就是公网地址，回传给用户/Agent** |
| `Recover success: [XXX]` | 断线重连成功 | 忽略/淡提示 |
| `recover to server timed out` | 重连失败 | 提示"网络波动，建议换节点" |
| `read from control connection EOF` | 控制连接读失败 | 网络波动 |
| `login to server failed: XXX` | 登录节点失败 | 提示检查网络/节点状态 |
| ``connect to local service [`XXX`] error: `YYY` `` | 连不上本地服务 | **最常见错误**：提示"你的本地服务没开 / 端口填错了" |
| `proxy conflict` | **隧道冲突**（重复开启） | ⚠️ 说明同一隧道在别处（官方启动器！）已经在跑 |
| `multi-instance racing, this one failed` | 多实例竞争 | ⚠️ 同上，本机有多个 frpc 抢同一条隧道 |
| `port already used` | 服务端端口被占 | 提示换远程端口 |
| `i/o deadline reached` | 节点过载 | 提示换节点 |
| `router config conflict` | URL 路由冲突 | 提示检查域名配置 |

**`Your ... proxy is available now. Use [...] to connect.` 这一行是插件能否"自己知道公网地址"的关键。**

### 6.1 DSH 插件的标准结构（从本机 `dsh-audiogen` 与 `dsh-system-net` 源码读出）

**`package.json` 的关键字段**（照 `dsh-audiogen` 抄）：

### 6.2 ⚠️ 关键技术风险：Node 没有 XSalsa20-Poly1305（**已实测**）

我实测了本机 Node v24.18.1 的 crypto 能力：

```
xsalsa20 相关: []                      ← 没有！
chacha 相关: [ 'chacha20', 'chacha20-poly1305' ]
是否支持 x25519 密钥交换: true         ← 有
x25519 生成成功: 44 bytes SPKI
```

**含义**：

- ✅ X25519 密钥交换：**Node 内置，可以直接用**；
- ❌ **XSalsa20-Poly1305（NaCl box）Node 内置 crypto 完全没有**。

所以**方案 C（完整的 argo 远程登录）必须引入一个第三方 npm 包**，候选：

| 包 | 说明 | 评价 |
|---|---|---|
| `tweetnacl` | NaCl 的经典 JS 实现，提供 `nacl.box` 正好就是 X25519+XSalsa20-Poly1305 | 零依赖、极小、久经考验，**首选** |
| `@noble/ciphers` | 更现代的审计过的实现，提供 `xsalsa20poly1305` | 也很好，作者信誉高 |
| 自己实现 XSalsa20 | — | ❌ **不要**，密码学自己写必出问题 |

**如果不想引依赖**：选方案 A 或 B（§4.2），**完全绕开这个问题**。这也是我建议 v1 用 A/B 的原因。

### 6.3 ⚠️ 另一个风险：凭据存储

- `dsh-audiogen` 用了 `z.dict(z.string().role('secret'))` 声明密钥字段 → DSH 的 settings 层会把带 `role('secret')` 的字段当敏感值处理；
- 插件需要把 Authorization 存到 `~/.dsh/` 下的设置文件（明文 YAML 的可能性较大，**需要你确认是否接受**，见 §10 问题 6）。

## 7. 建议的插件设计

### 7.1 设计原则

1. **不重复造轮子**：frpc 用**本机已装的那个**，不自己下载（除非你要求独立）；
2. **不和官方启动器打架**：启动隧道前先检测该隧道是否已被别人占用（见 §7.3）；
3. **最小惊讶**：默认只做"读"操作；写操作（新建/删除/启动）都要有明确回报和失败原因；
4. **公网地址是第一等公民**：任何输出都要包含"外部可通过什么地址访问"；
5. **合规优先**：带 UA、声明来源、不做自动签到。

### 7.2 v1 范围（建议）

**只做两件事，但做到位**：

| # | 能力 | 依赖接口 | 说明 |
|---|---|---|---|
| 1 | **查询**：列出我的隧道 + 在线状态 + **公网地址** + 剩余流量 + 节点列表 | 接口 14（仅需 token）+ 1 + 3 | 零登录成本，立刻可用 |
| 2 | **启停**：启动指定的隧道（`frpc -u <token> -p <id>`），解析日志拿到公网地址，随时停止 | frpc CLI | 核心价值所在 |

**v1 的 Agent 工具集**（建议 4 个）：

```
openfrp_status          → 账号概览（用户组、剩余流量、带宽、隧道数、当前运行的 frpc 进程）
openfrp_tunnels         → 列隧道（可筛选在线/离线），含每条的 connectAddress 公网地址
openfrp_start_tunnel    → 启动隧道（按 id 或名字），等日志出现 available 行后返回公网地址
openfrp_stop_tunnel     → 停止隧道
```

**v1 明确不做**：GUI 面板、frpc 下载/更新、登录流程、签到、节点测速。

### 7.3 v2 范围（验证 v1 值得之后再上）

```
openfrp_create_tunnel   → 自然语言建隧道（AI 自动挑节点、选协议、分配端口）
openfrp_edit_tunnel     → 改本地端口/IP/加密等
openfrp_delete_tunnel   → 删（要二次确认）
openfrp_nodes           → 节点列表（带推荐排序）
openfrp_logs            → 看某条隧道的实时日志
GUI 面板                → 侧边栏「OpenFrp」：隧道卡片 + 一键开关 + 实时日志
设置页                  → 登录方式、token、frpc 路径、合规声明
```

### 7.4 与官方启动器的共存策略（**v2 已定案**）

> v1 这里写的是"需要你选 A/B/C"。**v2 已定案**：不是"互斥"，而是**共存**——因为用户明确要用 OpenFrp 服务 MC 以外的用途，官方启动器必须留着。

关键事实（来自官方排错文档）：

> `proxy conflict` = **同一条隧道**被重复开启；`multi-instance racing` = 多个 frpc 争抢**同一条隧道**。

**冲突是按"隧道"计的，不是按"进程"或"账号"计的。** 所以两个 frpc 实例服务**不同隧道**时可以完全共存。

**定案的规则：**

| 谁 | 管哪些隧道 |
|---|---|
| 插件 | **只拥有它自己创建/启动的那些** |
| 官方启动器 | 继续管其余的 |
| 两者 | 共用一份 Authorization，各跑各的 frpc，互不干扰 |

**一条铁律：绝不启动一条已经在线的隧道。**
而且这个判断要**提前用 API 做**（`getUserProxies` 的 `online` / `status` 字段），
发现已在线就直接拒绝并告知 Agent"这条正被别处占用"，**不必等 frpc 报 `proxy conflict` 才发现**。

附带好处：这对要发 GitHub 的插件是更合理的设计——绝大多数用户都装着官方启动器，**共存是默认场景，不是特例。**

### 7.5 典型交互（做出来之后应该长这样）

> **你**：把本地的 8000 端口开出去，我要给朋友看
> **Agent**：`openfrp_tunnels` → 没有现成的 8000 隧道 → `openfrp_create_tunnel(type=http, local_port=8000)` → AI 从 `getNodeList` 里挑了"香港-5"（支持 http、未满载、用户组匹配、不需实名）→ `openfrp_start_tunnel` → 解析日志
> **Agent**：已经开好了，地址是 **`https://xxxx.openfrp.top`**，用的是香港-5 节点（延迟约 xx ms）。要我现在停掉吗？

### 7.7 安全设计要点

| 面 | 措施 |
|---|---|
| 凭据 | 只存 Authorization / token，不存密码；用 `role('secret')`；文档写清存放位置 |
| 隧道暴露 | **默认只提醒风险**：暴露 RDP / SSH / 数据库时给出警告（官方文档专门警告过 RDP 被爆破） |
| 误操作 | 删除隧道、重置 token 需要二次确认 |
| 日志 | 脱敏：日志里出现的 token / Authorization 要打码 |
| 合规 | UA 形如 `dsh-openfrp/0.1 (+https://github.com/<你>/…)`；README 与设置页都写"本项目由社区开发，OpenFrp 官方不负责技术支持"；**不实现自动签到** |

# v2 章节（需求已定稿）

## 12. v2 修订记录：v1 里被推翻的三处

### 12.1 痛点定位错了：不是"做不到"，是"DSH 没有眼睛"

v1 把需求理解成"让 AI 帮忙开隧道"。**错了。**

用户的真实表述：

> 我要开服，我叫 dsh 开服，他可以帮我提炼客户端，可以帮我选服务端、mod，可以帮我写启动脚本，这些不靠插件也可完成。
> 然后就是内网穿透，我可以进行设置，但是**这些设置、端口、节点，dsh 是看不到的，他只能指挥我做，做完复述给他**，然后连不上，找错，找不出来，这样耽误几个小时。
> 我第一次用 of 的程序，**我不知道上哪找 cname 地址**，仅靠用户转述是难以解决问题的。

**所以痛点是：人类被迫充当 DSH 的数据中转站。**
凡是一个信息只活在 GUI 里、或只活在人的脑子里，闭环就断了。

**这也解释了用户为什么会问"MC 服务端有没有接口让其他程序在运行期间读日志"**：
他要的不是"能开服"，是**证据级诊断**——DSH 应该说"返回了 xxx，这是 xxx 问题"，
而不是"java 闪退，可能是 xxxx"；玩家喊卡时，DSH 应该**自己装 mod、自己跑命令、自己分析**，
而不是"你下载 xxx，执行 xxx，截图给我"。

**由此得到判断插件价值的第一判据：**
> 如果插件的价值只是"省掉点面板的几步"，不值得做；
> 如果它的价值是**让 DSH 能自己看见日志、自己发命令、自己拿到地址、自己定位故障**，就值得做。

### 12.2 与官方启动器的关系错了：不是"夺权"，是"按隧道共存"

v1 一度得出"必须把官方启动器请出链路"的结论。**错了**，因为用户明确表示：

> 我在插件测试期间可以不使用官方启动器，但是这个**插件是为了我的世界做的，而我使用 of 不只是为了我的世界**，因此测试完，官方启动器我还是得用。

正确模型见 §7.4（已就地更正）：**冲突按隧道计，不按进程/账号计 → 插件只拥有自己创建的隧道 → 两者共存。**

### 12.3 插件边界错了：不是"隧道插件"，是"通用协调器"

v1 定位成"OpenFrp 隧道管理插件"。**改成**：**「本地服务 ↔ 隧道」的通用协调器，Minecraft 优先**（用户已确认）。

理由：
1. 要发 GitHub → 必须普适，**不能顺着调研者的三个服定制**；
2. 两侧本来就是通用的：一侧是"某个端口上的本地服务"，另一侧是"把端口暴露出去"；
3. 泛化后 MC 只是**一种适配器**，代码不必和 MC 绑死。

### 12.4 更正速查表

| v1 的说法 | v2 的更正 | 依据 |
|---|---|---|
| "生态空白，不是红海" | **OpenFrp 是空白，但"暴露本地服务"是红海**（60+ 同类插件） | §2.3 / 生态盘点 |
| "必须先回答 §10 的四个问题" | 已定：**(1) 完整浏览器授权登录 (2) 通用协调器，MC 优先** | 本文档 v2 |
| "必须把官方启动器请出链路" | **共存**，只拥有自己创建的隧道 | §7.4 / §12.2 |
| "MC 侧要考虑要不要夺权" | **不用夺权**。日志是文件、命令是 RCON，挂靠即可 | §13 |
| "读日志文件 ⇒ 能实时读" | v1 是**未经验证的断言**；v2 已**实测**（§13） | §13.2 |

## 13. MC 侧能力实测（v2 新增，这是用户反复追问的那个问题）

### 13.1 实验设计

为了回答"**MC 服务端运行期间，其他程序能不能实时读到日志？**"——注意 v1 那种"读一个静止的文件"是**不能**回答这个问题的。

- 环境：`C:\DSH\_mctest\`（隔离目录，**全程不碰用户的三个服**）
- 服务端：**原版 26.3**，从 Mojang 官方 `piston-meta` 下载（62,294,556 字节，sha1 `33680f5f…`，`javaVersion=25`）
- JVM：`C:\Program Files\Java\jdk-25.0.4\bin\java.exe`，`-Xms512M -Xmx1G`
- 端口：游戏 25999 / RCON 25998（避开用户在用的一切端口）
- 世界：`level-type=minecraft\:flat`，`online-mode=false`
- 实验后已**完全清理**：目录删除、无残留 java 进程、两个端口均已释放

> ⚠️ 副作用披露：启动服务端需要 `eula=true`，即**代用户同意了一次 Mojang EULA**（一次性测试实例，已删除）。

### 13.2 实测结果（原始数据）

| 墙钟时刻 | `logs/latest.log` 大小 | 文件 mtime | 状态 |
|---|---|---|---|
| 22:40:11 | 751 B | 22:40:10.915 | 启动中 |
| 22:40:17 | 2761 B | 22:40:17.155 | 到达 `Done (0.425s)! For help, type "help"` |
| 22:40:20 → 22:40:50（13 次采样） | **2761 B 不变** | **冻结在 22:40:17** | 空闲服务器**不产生日志** |
| **22:41:04（运行中发 RCON）** | **2992 B（+231）** | **22:41:04.483** | 新行时间戳 == 命令时间 |

运行中通过 RCON 发的命令**拿到了返回文本**：

```
> list
There are 0 of a max of 4 players online:
```

同一次操作让日志**多出三行**（时间戳与命令时刻完全一致）：

```
[22:41:04] [RCON Listener #1/INFO]: Thread RCON Client /127.0.0.1 started
[22:41:04] [Server thread/INFO]: [Not Secure] [Rcon] LIVE-224104
[22:41:04] [RCON Client /127.0.0.1 #2/INFO]: Thread RCON Client /127.0.0.1 shutting down
```

**结论：运行期间实时读日志 ✅、运行期间写命令 ✅，两条都实测通过。**

### 13.3 三条可直接用作握手信号的字符串

| 用途 | 日志字符串 | 备注 |
|---|---|---|
| **服务端就绪** | `Done (\d+\.\d+s)! For help, type "help"` | 只有出现它才算真的起来了 |
| **实际绑定端口** | `Starting Minecraft server on \*:(\d+)` | **拿它去建隧道**，而不是信配置文件 |
| **RCON 就绪** | `RCON running on ([\d.]+):(\d+)` | 说明命令通道可用 |

### 13.4 ⚠️ 意外发现（比结论本身更重要）

**空闲的 MC 服务端不写日志。** 那 47 秒里文件纹丝不动。

→ **「日志不动」绝对不能当成「服务端死了」。** 判活必须另用判据：
**进程存活 / 端口仍在监听 / RCON 探一下**。这条如果没做实验，插件上线后必然误报。

### 13.5 四条通道对照

| 通道 | 读日志 | 写命令 | 前提 | 适用版本 |
|---|---|---|---|---|
| **日志文件** `logs/latest.log` | ✅ 实时 | ❌ | 无 | Java 版通用约定 |
| **RCON** | ❌（仅请求-应答） | ✅ 任意命令 | 需 `enable-rcon=true` | **仅 Java 版** |
| **服务端管理协议**（JSON-RPC/WebSocket） | ❌ | ❌ 无任意命令 | `management-server-enabled=true` **且要处理 TLS keystore**（否则**服务端启动失败**） | 仅 Java 版 |
| **stdin/stdout** | ✅ 全量 | ✅ 任意命令 | 需自己持有进程 | Java + 基岩 |

> 管理协议能做的：`players`/`kick`/`operators`/`allowlist`/`bans`/`server save|stop|system_message`/`serversettings`/`gamerules` + 推送通知（`players/joined`、`players/left`）。
> **它不能执行任意命令、也不能订阅控制台日志** —— 所以插件的主通道仍是**日志文件 + RCON**，管理协议是锦上添花（§16 的 P6）。

### 13.6 未验证项（诚实列出）

- **Paper / Spigot / Forge / NeoForge 未实测**。它们同样写 `logs/latest.log`、同样支持 RCON（业界通用约定），但本次只实测了**原版 26.3** 与用户现存的 **Fabric 26.2** 日志。
- **基岩版（BDS）**：没有 RCON、没有管理协议。若要支持需要另做通道（stdin）。**本次未验证**。
- **DSH 宿主在会话结束时会不会回收子进程** —— 这条**未实测**，但它决定"能不能让插件托管长跑进程"，见 §17。

## 14. 最终设计（v2 定稿）

### 14.1 一句话定位

> **把"本地服务"和"隧道"这两侧都变成 DSH 能读、能写、能查的地方，并保证两边对同一个端口说同一种话。**
> MC 是首选场景，但契约是通用的。

### 14.2 三条设计铁律

1. **凡是 DSH 看不见的，都必须搬到它能看见的地方。**
   OpenFrp 的端口/节点/CNAME 只活在 Web 控制台 → 走 API；MC 的日志只活在控制台窗口 → 走文件 + RCON。
   **判断任何设计取舍，先问这一句。**
2. **证据优先于猜测。** 每个失败都必须落到一条机器可读的证据上（§14.7）。
3. **探测，不要配置；挂靠，不要接管；只拥有自己创建的东西。**

### 14.3 架构：两个控制面 + 一份契约

```
┌──────────────────── DSH 宿主进程（Node） ────────────────────┐
│  Agent  ──调用──▶ service_* / openfrp_* 工具                 │
│                        │                                     │
│   ┌────────────────────┼─────────────────────┐               │
│   ▼                    ▼                     ▼               │
│ 服务挂靠层          隧道控制层           注册表 + 对账         │
│ attach/tail/exec   auth/CRUD/frpc       registry.json        │
└───┬────────────────────┬─────────────────────┬───────────────┘
    │                    │                     │
    ▼                    ▼                     ▼
logs/latest.log      api.openfrp.net       ~/.dsh/dsh-openfrp/
RCON :25575          access.openfrp.net      registry.json
(只读/发包)          自己的 frpc 进程         自己的 frpc 目录
```

**关键：MC 侧只读文件 + 发 RCON 包 → 不持有进程 → 用户怎么开的服都能接上。**

### 14.4 通用挂靠契约（这是"通用"的落点）

```
attach(target) → ServiceHandle
  target: 一个目录 | 一个端口 | 一个显式描述
  ServiceHandle = {
    id, kind, root,
    localPort,                       // 优选从日志读到的「实际端口」
    readiness: { pattern, timeout },  // 就绪信号
    logs:  { path, encoding },        // 日志源
    exec:  { kind: 'rcon'|'stdin'|'none', host, port, passwordRef },
    health:{ kind: 'tcp'|'http'|'process', spec }
  }
```

**适配器（adapter）机制**——每种服务一个适配器，`kind` 决定怎么填这个 handle：

| adapter | 探测依据 | localPort | 就绪信号 | 日志 | 命令 |
|---|---|---|---|---|---|
| `minecraft-java` | 目录里有 `server.properties` + `logs/` | 日志里的实际绑定端口 | `Done (…)!` | `logs/latest.log` | RCON（从 server.properties 读） |
| `generic-port` | 只给端口 | 显式给定 | 可选 HTTP/TCP 探活 | 无 | 无 |
| `static-web` | 给了根目录和端口 | 显式给定 | `GET /` 200 | 无 | 无 |

> **普适性要求：任何路径、版本、加载器都不得写死。** `minecraft-java` 只认**约定**（`server.properties` / `logs/latest.log`），不认用户的目录名。

### 14.5 服务注册表（跨会话的"事实来源"）

路径：`~/.dsh/dsh-openfrp/registry.json`

```jsonc
{
  "services": [{
    "id": "vanillaplus",              // 用户/agent 可读的短 id
    "kind": "minecraft-java",
    "root": "C:/DSH/mcserver/VanillaPlus-26.2",
    "localPort": 25565,               // 实际值
    "logs": { "path": "logs/latest.log" },
    "exec": { "kind": "rcon", "host": "127.0.0.1", "port": 25575, "passwordRef": "svc:vanillaplus:rcon" },
    "tunnel": { "provider": "openfrp", "proxyId": 123456, "public": "cn-xx.openfrp.top:25565",
                "frpcPid": 1234, "ownedBy": "plugin" },
    "state": "running",
    "updatedAt": "2026-10-04T22:41:04+08:00"
  }]
}
```

**这份文件存在的唯一理由**：让新会话的 DSH 能自己捡回"现在到底在跑什么、映射到哪"。
**没有它，"自行分析自行解决"就无从谈起。**

### 14.6 隧道侧策略（只拥有自己的）

1. **前置检查**：`getUserProxies` → 目标隧道 `online==true` 就**拒绝**，并说明"正被别处（很可能是官方启动器）占用"；
2. **自己的 frpc**：自己的二进制 + 自己的运行目录（`~/.dsh/dsh-openfrp/frpc/`），**绝不 kill 别人的进程**；
3. **启动参数**：`-u <token> -p <id> --disable-log-color --noupdate`，`windowsHide:true`，`env` 里**清掉 8 个代理变量**（Windows 下 key 大小写要去重）；
4. **就绪**：解析 stdout 的 ``Your `X` proxy is available now. Use [`addr`] to connect.`` → 抓出公网地址；
5. **停止**：`taskkill /F /T /PID`（Windows）/ `SIGTERM`（其余）；**不停别人的**。

### 14.7 证据级诊断表（这是"自行分析自行解决"的实质内容）

| 现象 | 要看的证据 | 结论 |
|---|---|---|
| 玩家连不上 | frpc stdout `connect to local service [x] error` | **本地端口与隧道 `local_port` 不一致** → 回 §14.4 重新对齐 |
| 隧道起不来 | frpc `proxy conflict` / `multi-instance racing` | 同一条隧道在别处已开（多半是官方启动器） |
| 服务端没起来 | `logs/latest.log` 里**没有** `Done (`；且有 `FAILED TO BIND TO PORT` | 端口被占 |
| 服务端没起来 | 有 `Done (` 但 RCON 连不上 | `enable-rcon` 没开 / 端口密码不对 |
| 服务端崩了 | `crash-reports/*.txt` + 日志尾部堆栈 | 具体模组/类 → 直接给出类名 |
| 玩家喊卡 | RCON `spark tps` / `spark health show --memory` / `spark profiler start --timeout N` + `stop --save-to-file` | 具体是哪个模组/线程吃掉了 tick |
| 日志长时间不动 | **不要判死**（§13.4）→ 转去查进程/端口/RCON | 空闲服务器本来就不写日志 |

> spark 已实测存在于用户三套服中；即便缺失，DSH 也能自己从 Modrinth 取 jar 放进 `mods/`——这正是"自己下载、自己执行、自己分析"。

## 15. Agent 工具面

**原则：少而稳、动作用 action 分组、错误必须带证据。**

| 工具 | action | 作用 |
|---|---|---|
| `service_attach` | — | 挂靠一个目录/端口（自动探测 kind），写入注册表 |
| `service_list` | — | 列出所有已挂靠服务 + 状态 + 隧道 + 公网地址（**新会话第一件事**） |
| `service_status` | — | 对账：进程/端口/RCON/隧道 逐项核实，报告漂移 |
| `service_logs` | — | 实时读日志（支持只看尾部 N 行 / 等待某个 pattern） |
| `service_exec` | — | 发命令（优先 RCON）并返回**服务端的原始回应** |
| `service_expose` | `up` / `down` / `list` | 建/启隧道并返回公网地址；`down` 释放 |
| `openfrp_account` | `login` / `poll` / `status` / `logout` | 登录（argo 流程）、状态、登出 |
| `openfrp_tunnel` | `list` / `create` / `edit` / `delete` / `nodes` | 隧道与节点管理（含 CNAME/`connectAddress`） |

**工具描述必须写清"什么时候用它"**，否则 Agent 会绕过插件回退到"指挥用户"的老路——那正是本插件要消灭的行为。

## 16. 分阶段实施计划（P0～P7）

技术栈对齐本机已有插件（`dsh-audiogen`）：**TypeScript + tsdown + React 18 + CSS Modules**，
宿主侧 `apply(ctx, config)`，浏览器侧 `dsh.client.platform=web`，`cordis.patch.yml` 挂载。

| 阶段 | 目标 | 可实测的验收点 |
|---|---|---|
| **P0 脚手架** | 建 `C:\DSH\dsh-openfrp\`（git init），package.json / tsconfig / tsdown / cordis.patch.yml / 设置骨架 | `pnpm build` 通过；`import()` 不报错 |
| **P1 认证（argo）** | `tweetnacl` + X25519 密钥对；`requestLogin` → 拉起浏览器 → 5s×60 轮询 → 解密 Authorization；**响应头轮转**；凭据用 `role('secret')` 存 | **真跑通**：拿到 Authorization 并能成功调 `getUserInfo`；故意不授权 → 5 分钟超时且不刷 429 |
| **P2 OpenFrp 客户端** | REST 封装（**必带 UA**）、`flag/msg` 错误模型、`getUserProxies` / `getNodeList` / `newProxy` / `editProxy` / `removeProxy` / `changeProxy` | **真跑通**：列出账号隧道并打印 `connectAddress` / `connection` / CNAME（**正是"上哪找 CNAME"那个痛点**） |
| **P3 服务挂靠** | `minecraft-java` 适配器：探测 `server.properties` + `logs/`；读实际端口；RCON 客户端；日志 tail | **真跑通**：对一个运行中的服，实时读到新日志行 + 发出命令拿到回应 |
| **P4 暴露闭环** | 自持 frpc（只拥有自己的隧道）+ 前置 `online` 检查 + 就绪握手 + 公网地址回填注册表 | **真跑通**：一句话把服务暴露出去拿到可访问地址；**同时开着官方启动器也不冲突** |
| **P5 诊断/对账** | `service_status` 对账 + §14.7 诊断表全部落地 | **故意制造 4 种故障**（端口不一致 / 端口被占 / RCON 未开 / 模组崩溃），每种都给出证据级结论 |
| **P6 增强** | 服务端管理协议适配（结构化玩家/规则管理、`players/joined` 推送）、自动装 spark | 能通过管理协议踢人/改规则；缺 spark 时能自动装上 |
| **P7 发布** | GUI 面板（隧道卡片 + 实时日志 + 设置页）、README（**含 OpenFrp 声明与免责**）、GitHub 开源、可选 npm | 按工作区规范走完「看结构 → 看截图 → design_audit」三步 |

**P3/P4 的验收可以直接复用 §13 的实验方法**——在隔离目录里拉起一个原版服务端来测，不碰用户的服。

## 17. 风险与开放问题

| # | 风险 / 开放问题 | 等级 | 处置 |
|---|---|---|---|
| 17.1 | **DSH 宿主会不会在会话结束时回收子进程**（决定能否托管长跑服务端） | 🔴 高 | **必须实测**：起一个长命令，结束会话，看子进程是否存活。若会被回收，则服务端必须**由用户/独立脚本持有**，插件只挂靠 |
| 17.2 | OpenFrp 服务条款：必须带 UA、必须明显位置声明、**禁止自动签到**、商用需书面授权 | 🔴 高 | 全部做进实现 + README + 设置页说明 |
